# Промпт для Codex: SPA для интеллектуальной подготовки фотографий

Ты — ведущий frontend-разработчик и архитектор. Создай законченное, пригодное к использованию одностраничное веб-приложение, которое с помощью DeepSeek Vision анализирует фотографии, разумно кадрирует их под несколько заранее заданных форматов, выполняет умеренную цветокоррекцию локально в браузере, приводит файлы к заданным размерам и предельному объёму и выдаёт результаты одним ZIP-архивом.

Не ограничивайся прототипом интерфейса. Реализуй работающий end-to-end MVP, тесты, документацию и автоматическую публикацию на GitHub Pages.

## 1. Ограничения и базовая архитектура

- Приложение — статическое SPA без собственного backend.
- Хостинг — публичный GitHub Pages.
- Стек: React + TypeScript + Vite. Если в существующем репозитории уже выбран сопоставимый современный стек, сохрани его и объясни решение в README.
- Все изображения обрабатываются локально в браузере. DeepSeek получает уменьшенную копию фотографии только для визуального анализа и возвращает только инструкции преобразования. Не использовать генерацию или редактирование изображения моделью.
- Пользователь самостоятельно вводит свой DeepSeek API key (BYOK).
- Ключ существует только в памяти текущей вкладки. Не записывать его в localStorage, sessionStorage, IndexedDB, URL, логи, analytics, error reporting или состояние, которое сериализуется.
- Добавить явное предупреждение: это публичное клиентское приложение, введённый ключ доступен выполняющемуся в странице JavaScript; пользоваться следует только доверенной опубликованной сборкой и отдельным ключом проекта с небольшим лимитом расходов. В README отдельно описать, что безопасная многопользовательская production-версия потребует backend/edge-proxy и не должна раздавать общий секрет браузерам.
- Не добавлять analytics, telemetry и сторонние сетевые запросы, кроме DeepSeek API.
- Не отправлять фотографии куда-либо ещё.
- Приложение должно работать после обычного `npm install && npm run dev`, собираться через `npm run build` и корректно открываться из подпути GitHub Pages.

## 2. Пользовательский сценарий

1. Пользователь открывает приложение.
2. Вводит DeepSeek API key. Поле — password с кнопкой показать/скрыть.
3. Загружает одну или несколько фотографий через drag-and-drop или диалог выбора файлов.
4. Видит превью, имя, исходные размеры и объём каждого файла; может удалить отдельные фотографии или очистить список.
5. Выбирает один или несколько форматов из предопределённого каталога.
6. Может создавать, редактировать, дублировать и удалять пользовательские форматы.
7. Может ввести общий дополнительный промпт для всей партии, например: «человек должен оставаться по центру» или «главный объект — сцена, а не зрители».
8. При необходимости может задать отдельное уточнение для конкретной фотографии.
9. Нажимает «Подготовить изображения».
10. Видит прогресс отдельно по каждой фотографии: ожидание → анализ → проверка инструкции → рендеринг вариантов → сжатие → готово / ошибка.
11. До скачивания видит превью каждого результата, итоговые размеры в пикселях, формат, реальный объём файла и предупреждения.
12. Может скачать отдельный файл или один ZIP со всеми успешно подготовленными файлами.
13. Неуспешные элементы можно повторить без повторной обработки готовых.

Если фотографии или форматы не выбраны, кнопка запуска недоступна и интерфейс ясно объясняет причину.

## 3. Модель данных формата

Используй тип примерно следующего вида:

```ts
type OutputFormat = {
  id: string;
  group: string; // площадка или группа
  name: string; // человекочитаемое название
  width: number; // точная ширина результата в px
  height: number; // точная высота результата в px
  mimeType: "image/jpeg" | "image/png";
  extension: "jpg" | "png";
  maxBytes: number;
  prompt?: string; // дополнительные требования этого формата
  filenameTemplate: string; // например {sourceBase}__{formatSlug}.{ext}
  builtIn: boolean;
};
```

Требования к пользовательским форматам:

- обязательны название, ширина, высота, тип файла и максимальный объём;
- ширина и высота — положительные целые числа в разумных пределах;
- максимальный объём вводится в КБ, внутри хранится в байтах;
- комментарий/prompt необязателен;
- шаблон имени файла поддерживает как минимум `{sourceBase}`, `{formatName}`, `{formatSlug}`, `{width}`, `{height}`, `{ext}`;
- валидировать имя файла и удалять запрещённые для файловых систем символы;
- пользовательские форматы и изменения каталога сохранять в localStorage; API key туда никогда не сохранять;
- предусмотреть «Восстановить стандартные форматы» и импорт/экспорт каталога в JSON.

## 5. DeepSeek API и выбор модели

Используй DeepSeek Responses API с image input и Structured Outputs по JSON Schema. Перед реализацией сверь синтаксис с актуальной официальной документацией DeepSeek; не полагайся на устаревшие примеры SDK.

Используй модель:

- **Vision, по умолчанию:** `deepseek-flash` — текущая модель DeepSeek API с поддержкой изображений, Responses API и структурированного JSON.
- `deepseek-v4-pro` не использовать: модель предназначена для сложных текстовых задач и не поддерживает изображения.

Не использовать image-generation model: задача модели — только анализ и план преобразования.

Модель выбирается централизованно в конфигурации. Не размазывай строковый ID по проекту. Обрабатывай ситуацию, когда модель недоступна аккаунту пользователя, и показывай понятную ошибку.

## 6. Оптимальный pipeline запросов

Делай **один API-запрос на одну исходную фотографию**, передавая в нём все выбранные форматы. Не делай отдельный vision-запрос для каждой пары «фото × формат»: модель должна один раз понять сцену, выделить важные объекты и затем предложить отдельное преобразование для каждого целевого aspect ratio.

Для каждой фотографии:

1. Прочитать и корректно применить EXIF orientation.
2. Подготовить отдельную уменьшенную копию только для анализа моделью, сохранив достаточную детализацию. Оригинал оставить локально для финального рендера.
3. Передать модели:
   - анализируемое изображение;
   - его фактическую ширину и высоту после нормализации ориентации;
   - массив выбранных форматов;
   - встроенный системный prompt;
   - общий пользовательский prompt;
   - prompt конкретной фотографии;
   - prompt каждого формата.
4. Получить один строго типизированный JSON с общей оценкой фотографии и отдельной инструкцией для каждого format ID.
5. Проверить ответ JSON Schema и локальными семантическими правилами.
6. Для валидных инструкций выполнить обработку исходного изображения локально.
7. Если ответ формально или семантически невалиден, выполнить не более одного повторного запроса. Передать список конкретных ошибок и потребовать исправленный полный объект без изменения format IDs.
8. При повторной ошибке показать её пользователю; не зацикливаться.

Ограничь параллелизм API-запросов, например до двух фотографий одновременно, и добавь exponential backoff с jitter для временных ошибок и rate limits. Отмена через AbortController должна реально прекращать новые задачи и активные запросы.

## 7. Встроенный системный prompt для анализа фотографии

Храни prompt отдельно от UI-кода, чтобы его было легко редактировать. Его смысл:

```text
Ты — специалист по подготовке редакционных и рекламных фотографий. Проанализируй исходную фотографию и для каждого переданного целевого формата верни только допустимую по схеме инструкцию локальной обработки.

Главная задача — получить естественный кадр заданного aspect ratio без генерации новых объектов и без удаления объектов. Сохраняй главный смысл сцены, лица, головы, руки, важные предметы, надписи и композиционные связи. Не допускай случайного обрезания лица, макушки, подбородка, кистей и ключевых объектов. При конфликте требований выбирай наиболее содержательный и естественный кадр.

Сначала определи главные объекты, лица, визуальный центр, важные области и нежелательные края. Затем для каждого формата выбери crop прямоугольник внутри исходного изображения с точным aspect ratio целевого формата. Если пользователь не дал специальных указаний, применяй профессиональные правила композиции: сохраняй главный объект, оставляй разумное пространство по направлению взгляда или движения, учитывай правило третей, горизонт и визуальный баланс.

Разрешена только умеренная неразрушающая коррекция: экспозиция, контраст, насыщенность, температура, светлые области, тени и лёгкая резкость. Не меняй узнаваемость людей и объектов. Не придумывай содержимое. Не обещай удалить текст или логотип цветокоррекцией: если требование нельзя выполнить кадрированием без потери главного сюжета, укажи предупреждение.

Все координаты crop должны быть нормализованы относительно уже ориентированного исходника: x, y, width, height находятся в диапазоне 0..1. Crop обязан полностью находиться внутри изображения и иметь aspect ratio целевого формата с допустимой погрешностью. Верни инструкцию для каждого и только каждого переданного formatId.
```

Пользовательские prompts считаются уточнениями, но не могут отменять технические ограничения и запрет на выдумывание содержимого.

## 8. Структура ответа модели

Спроектируй строгую JSON Schema и соответствующие TypeScript/Zod-типы. Ожидаемая структура:

```ts
type AnalysisResult = {
  sourceSummary: string;
  subjects: Array<{
    kind: "person" | "face" | "object" | "text" | "logo" | "other";
    description: string;
    importance: number; // 0..1
    box: { x: number; y: number; width: number; height: number };
  }>;
  outputs: Array<{
    formatId: string;
    crop: { x: number; y: number; width: number; height: number };
    adjustments: {
      exposure: number; // -1..1
      contrast: number; // -1..1
      saturation: number; // -1..1
      temperature: number; // -1..1
      highlights: number; // -1..1
      shadows: number; // -1..1
      sharpen: number; // 0..1
    };
    warnings: string[];
    rationale: string;
  }>;
};
```

Если некоторые коррекции слишком сложно качественно реализовать в MVP, не игнорируй их молча: либо реализуй понятную детерминированную аппроксимацию, либо сузь схему и документируй принятое решение. Не включай операции, которые приложение фактически не умеет исполнять.

## 9. Локальная валидация инструкций

Даже при Structured Outputs обязательна семантическая проверка:

- присутствуют все выбранные format IDs ровно по одному разу;
- неизвестных format IDs нет;
- все числа конечны;
- `x`, `y`, `width`, `height` находятся в диапазоне 0..1;
- `width > 0`, `height > 0`, `x + width <= 1`, `y + height <= 1`;
- aspect ratio crop совпадает с `targetWidth / targetHeight` в заданной погрешности;
- crop в исходных пикселях имеет достаточный размер; upscale явно помечается предупреждением;
- значения коррекции находятся в разрешённых диапазонах;
- инструкция не содержит неподдерживаемых операций.

Небольшую численную погрешность aspect ratio исправляй локально безопасным расширением или сужением crop внутри границ. Существенную ошибку отправляй на однократный repair retry.

## 10. Обработка изображения в браузере

- Нормализуй EXIF orientation до анализа и рендера, чтобы координаты модели совпадали с Canvas.
- Используй исходный файл для финального результата, а не уменьшенное vision-превью.
- Crop выполняй строго по нормализованным координатам.
- Итог должен иметь **точно** заданные width × height.
- Для качественного уменьшения используй проверенную библиотеку ресемплинга вроде `pica` либо эквивалент с хорошим качеством. Обоснуй выбор.
- Цветокоррекция должна быть детерминированной. Все параметры ограничивай безопасными диапазонами.
- Учитывай цветовой профиль и браузерные ограничения; стремись к sRGB и документируй возможные различия между браузерами.
- Не увеличивай разрешение молча. Разреши upscale для соблюдения точного формата, но показывай предупреждение о возможной потере качества.

### Ограничение объёма

Для JPEG:

1. Сначала рендерить с высоким качеством.
2. Если файл больше `maxBytes`, подобрать качество бинарным поиском через `canvas.toBlob`.
3. Использовать весь допустимый диапазон quality `0–1`, выбирая максимальное значение, при котором фактический Blob укладывается в лимит.
4. Проверять фактический размер Blob, а не оценку.
5. Если даже минимальное quality не укладывается, детерминированно снижать внутреннюю детализацию через уменьшение и качественное обратное масштабирование, не меняя заданные итоговые пиксельные размеры. Найти максимальный уровень детализации, при котором лимит достижим, затем повторно подобрать максимальный quality.
6. Только если даже минимальное fallback-представление не укладывается, отметить результат как не соответствующий лимиту и предложить скачать его отдельно.

Для PNG:

- Не притворяться, что параметр quality у `toBlob("image/png")` гарантирует сжатие.
- Использовать реальную lossless/quantization-стратегию в браузере либо честно показать, что лимит недостижим.
- Если применяется palette quantization, показать это в деталях результата и покрыть тестами.

После кодирования обязательно проверить:

- точные размеры в пикселях;
- MIME type;
- расширение;
- фактический объём `<= maxBytes` либо явный статус нарушения;
- возможность декодировать полученный Blob обратно как изображение.

## 11. ZIP и имена файлов

- Собрать успешные результаты в ZIP, например с помощью JSZip.
- Структура: папка исходной фотографии → подготовленные варианты.
- Предотвращать коллизии имён детерминированными суффиксами.
- Добавить в ZIP `manifest.json` с исходным именем, format ID, целевыми и фактическими параметрами, применённым crop, коррекциями, размером Blob и предупреждениями.
- Не включать API key, исходные изображения, prompts пользователя или полный ответ API в manifest.

## 12. Интерфейс

Сделай аккуратный адаптивный интерфейс на русском языке:

- секция API key и профиль модели;
- загрузка фотографий;
- каталог форматов, сгруппированный по площадкам;
- редактор пользовательского формата;
- общий prompt;
- очередь и прогресс;
- галерея результатов «до/после»;
- понятные ошибки и кнопки повторной обработки;
- кнопки «Скачать файл» и «Скачать всё ZIP».

Покажи пользователю приблизительное число API-запросов до запуска: оно равно количеству фотографий, плюс возможные повторы. Не обещай точную стоимость без актуального расчёта image tokens.

Обеспечь базовую accessibility: labels, клавиатурная навигация, focus states, достаточный контраст, aria-live для статусов.

## 13. Ошибки и устойчивость

Обработай минимум:

- неверный или отсутствующий API key;
- модель недоступна;
- CORS/network error;
- rate limit и временные 5xx;
- отказ модели;
- невалидный structured output;
- семантически неверные crop-инструкции;
- слишком большой или неподдерживаемый файл;
- недостаток памяти браузера;
- невозможность уложить изображение в лимит;
- отмену операции пользователем.

Не выводи API key и чувствительные данные в тексте ошибок или console. Object URLs освобождай через `URL.revokeObjectURL`, большие bitmap/canvas освобождай после использования. Не держи одновременно в памяти все полноразмерные декодированные изображения.

- проверки и коррекции crop;

## 18. Критерии приёмки

- SPA собирается и может быть опубликовано на GitHub Pages;

- тесты и production build проходят;
